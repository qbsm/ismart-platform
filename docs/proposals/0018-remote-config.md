# Proposal 0018: Удалённая конфигурация сайтов с api.ismart.pro

**Status:** Proposed
**Дата:** 2026-08-09
**Reference implementation:** нет — предложение опережает реализацию; ближайший работающий
родственник — rescue-канал (`src/Notification/Channel/RescueChannel.php`), который уже ходит
на тот же приёмник и авторизуется тем же способом
**Scope:** core — `src/Service/`, `config/settings.php`, `templates/base.twig`,
`assets/js/main.js`; на стороне приёмника — `rescue/` в `api.ismart.pro`
**Related:** ADR-0005 (каналы уведомлений), ADR-0012 (CSP без allowlist сторонних),
`docs/reference/env.md`, `docs/architecture/distillation.md`

---

## Контекст

Поведение сайта сегодня целиком зашито в выкладку. Чтобы поменять текст модалки, выключить
сломанный канал или притормозить отправку событий, нужен полный цикл: коммит → pull на
каталоге → пересборка бандлов → чистка twig-кэша. На парке из 27 сайтов это дорого и
ненадёжно — 2026-08-09 одна правка фронта потребовала pull на девяти каталогах, причём часть
выкладок молча не доехала (`pull: Aborting` из-за разложенных руками файлов, старый бандл
из-за несброшенного кэша).

Цена проявляется там, где реакция должна быть быстрой:

- кабинет CallTouch на `promo.avilon-changanauto.ru` месяц отдавал отказы — выключить канал
  можно было только выкладкой;
- дефект в отправке событий воронки (`sendBeacon` шлёт POST, приёмник ждал GET) чинился
  раскаткой по всему парку, хотя достаточно было бы выключить модуль на час;
- тексты и офферы правит маркетинг, а релизный цикл — мы.

Общее у этих случаев одно: меняется **параметр поведения**, а не код. Такие параметры и
предлагается вынести на приёмник, который уже знает про все сайты (реестр `Site`, 27 записей)
и уже принимает от них запросы.

## Решение

Приёмник отдаёт сайту JSON-конфиг. Конфиг **накладывается поверх** значений из
`config/settings.php` и `.env`, а не заменяет их: код остаётся источником дефолтов, удалённый
конфиг — оверлеем по разрешённому списку ключей.

### Два слоя, а не один

| Слой | Кому | Как доставляется | Что можно класть |
| --- | --- | --- | --- |
| `server` | бэкенду сайта | HTTP-запрос PHP → api, файловый кэш | включённость каналов, таймауты, лимиты, стоп-листы, расписание |
| `public` | браузеру | вливается в `window.appConfig` (`templates/base.twig:133`) | выключатели модулей фронта, тексты, задержки, доля семплирования |

Разделение обязательное. Всё, что попадает в `public`, оказывается в исходнике страницы —
там не должно быть ничего, чего нет в разметке и так. Секреты (`CALLTOUCH_TOKEN`,
`TELEGRAM_BOT_TOKEN`, ключ сервис-аккаунта Sheets) в конфиге не участвуют вообще: они
остаются в `.env` сайта. Иначе компрометация приёмника означает утечку всех кабинетов сразу —
цену этого мы уже видели, когда `.env` оказался доступен в докруте семи промо-сайтов.

Публичный слой едет **вместе со страницей**, а не запросом из браузера. Это принципиально:
запрос из JS к `api.ismart.pro` добавил бы блокирующий раунд к стороннему хосту, мигание
интерфейса до применения настроек и обязательную правку CSP на всех сайтах — при том что
ADR-0012 сознательно оставляет политику широкой и не ведёт allowlist.

### Контракт

```
GET https://api.ismart.pro/v1/config
X-Site: promo.foton-avilon.ru
X-Site-Key: <hmac(RESCUE_SALT, домен)>   ← только вне нашего периметра
If-None-Match: "42"
```

```json
{
  "version": 42,
  "ttl": 300,
  "server": {
    "channels": { "calltouch": { "enable": false }, "rescue": { "timeout": 5 } },
    "blocklist": { "phones": ["79990000*"], "ips": [] }
  },
  "public": {
    "widget": { "autoshow_delay": 8, "enabled": true },
    "funnel": { "enabled": true, "sample": 1.0 },
    "texts": { "callback_title": "Перезвоним за 1 минуту" }
  },
  "sig": "hmac-sha256 тела без поля sig"
}
```

Авторизация переиспользуется целиком: приёмник сверяет домен с адресом запроса (`rescue/auth.py`),
ключ нужен только там, где A-запись смотрит на CDN или общий адрес клиента. Ответ подписан
той же солью — сайт отбрасывает конфиг с несошедшейся подписью и остаётся на прежнем.
`ETag` по версии делает регулярный опрос почти бесплатным: обычный ответ — `304`.

### Наследование, иначе 27 копий одного значения

Конфиг собирается на приёмнике из трёх уровней: **платформа → группа → сайт**. Группа — это
клиент или бренд (авилон-промо, kumho, italycommunity). Выключить воронку на всех промо-сайтах
Авилона должно быть одним действием, а не двадцатью. Разрешение — простое слияние словарей
сверху вниз, побеждает более конкретный уровень.

### Применение на стороне сайта

```
config/settings.php  (дефолты)
        ↓ merge по whitelist
cache/remote-config.json  (последний удачный ответ + время получения)
        ↓
$settings['calltouch']['enable']   →  NotificationDispatcher
$config['public']                  →  window.appConfig  →  модули фронта
```

Ключевое ограничение: **сетевой запрос не должен участвовать в рендере страницы**. Обновление
кэша идёт отдельным процессом — крон раз в 5 минут (`php tools/ops/config-pull.php`), рядом с
существующими `cache/google-sheets` и `cache/rate_limit`. Внутри запроса читается только файл.
Если файл старше `ttl` вдвое и крон явно сломан, допускается разовое обновление в запросе с
таймаутом 1 с под файловым локом — страховка, а не основной путь.

Накладываются только ключи из явного списка в коде (`RemoteConfigService::ALLOWED`). Всё
остальное в ответе игнорируется молча. Без этого удалённый конфиг превращается в удалённое
исполнение: возможность поменять `twig.cache` или `paths` — это уже не настройка поведения.

## Структура файлов

| Файл | Что делает |
| --- | --- |
| `src/Service/RemoteConfigService.php` | читает кэш, проверяет подпись, сливает по whitelist |
| `tools/ops/config-pull.php` | крон: запрос к api, `ETag`, атомарная запись кэша |
| `config/settings.php` | секция `remote_config` (`enable`, `url`, `ttl`, `key`) |
| `templates/base.twig:133` | добавляет `public`-слой в `window.appConfig` |
| `.env` | `CONFIG_ENABLE`, `CONFIG_URL`, `CONFIG_TTL` — префикс = имя канала, как в `docs/reference/env.md` |
| `rescue/config.py` + `SiteConfig` (api) | хранение, слияние уровней, версия, подпись |

## Отказоустойчивость

Три уровня деградации, ни один не роняет сайт:

1. свежий кэш — обычная работа;
2. устаревший кэш (api недоступен) — работаем на нём, пишем предупреждение в лог;
3. кэша нет вовсе (первый запуск, битый файл) — значения из `config/settings.php`.

Отдельно — «ядовитый конфиг»: версия, после которой сайт отвечает ошибкой. Предохранитель
простой: `bin/config-pull.php` после записи дёргает главную страницу; если ответ не 2xx,
кэш откатывается на предыдущую версию и в лог уходит запись. На первом этапе этого достаточно,
автоматический глобальный откат по телеметрии — задача следующего.

## Наблюдаемость

Сайт сообщает приёмнику применённую версию: `config_version` в payload заявки и в событиях
воронки. Тогда видно, какая версия реально работает на каждом сайте, — расхождение между
«поменяли в админке» и «доехало» перестаёт быть слепым пятном, как сейчас с бандлами.
В ночной обход добавляется проверка: сайты, чья версия отстаёт от текущей больше чем на час.

## Что в конфиг не кладём

Вёрстку и шаблоны, схему данных, маршруты, содержимое страниц (`data/json/`), секреты.
Граница проходит по вопросу «нужно ли ревью?»: если изменение стоит смотреть глазами и
откатывать через git — это код, а не конфиг. Удалённый конфиг управляет **параметрами
поведения**, и соблазн расширять его дальше нужно осознанно сдерживать: конфиг без ревью,
влияющий на 27 сайтов, — это деплой с другими правилами, а не «просто настройка».

## Этапы

1. Только публичный слой на одном сайте: выключатели модулей фронта, тексты модалок, доля
   семплирования воронки. Ничего необратимого, проверяется за день.
2. Серверный слой: включённость каналов, таймауты, стоп-листы. Здесь появляется реальная
   польза аварийного выключателя.
3. Группы, canary-раскатка (`rollout.percent`), журнал версий с откатом, редактирование
   в админке приёмника.

## Отвергнутые варианты

- **Запрос конфига из браузера.** Блокирующий раунд к стороннему хосту, мигание, правка CSP
  на всех сайтах вопреки ADR-0012. Отвергнут.
- **Push с приёмника на сайт (вебхук).** Требует открытого эндпоинта и авторизации на каждом
  из 27 сайтов — новая поверхность атаки ради экономии пяти минут задержки. Возможен позже
  как ускорение поверх pull: подписанный сигнал «сбрось кэш».
- **Конфиг в git deployment'а.** Это ровно то, что есть сейчас, и чью цену описывает контекст.
- **Единый конфиг без разделения на слои.** Рано или поздно серверное поле попадёт в HTML;
  разделение должно быть в контракте, а не в дисциплине.

## Открытые вопросы

- Кто и через что редактирует: админка Django на приёмнике сейчас недоступна (учёток нет,
  `/admin/` отдаёт 302) — нужна учётка и минимальная форма редактирования.
- Нужен ли аудит изменений (кто, когда, что) — вероятно да, раз конфиг влияет на прод.
- Что делать при рассинхроне: PHP уже прочитал версию 42, страница отдана, а модуль фронта
  ждёт поля из 43. Вероятно, достаточно правила «поля только добавляются, старые не
  переименовываются» — то же, что с шапкой таблицы заявок.

## Acceptance

- Сайт с недоступным `api.ismart.pro` работает и отдаёт 200 на всех типах страниц.
- Конфиг с испорченной подписью игнорируется, в логе — запись, поведение прежнее.
- Ключ вне whitelist не влияет ни на что.
- Изменение публичного поля в приёмнике доезжает до сайта за один интервал крона без выкладки.
- `config_version` виден в заявке и в ночном обходе.

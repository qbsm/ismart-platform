## Лидогенерация: 98 лидов не долетали до CallTouch (починено)

По запросу «все фикси по сайтам, особенно отправки форм и лидогенерация» разобрана
вся связка форм с CallTouch на 13 сайтах.

### Причина

`form.php` собирал payload так:

```php
'sessionId' => $_COOKIE['_ct_session_id'] ?? $data['sessionId'] ?? '',
```

Кука `_ct_session_id` — единственный источник: `sessionId` **нигде во фронте не
отправляется**, поэтому ветка `$data['sessionId']` никогда не срабатывала. Когда куки нет
(блокировщик рекламы, ITP, отложенная на `load+3s` загрузка трекера), в API уходила
**пустая строка**, и CallTouch отвергал заявку целиком.

Контракт подтверждён пробой по живому API (телефон пустой — лид не создаётся):

| запрос | ответ |
|---|---|
| **без** ключа `sessionId` | одно нарушение: `phone` |
| `sessionId: ""` | `phone` + `sessionId: «Значение должно быть больше чем 0»` |

То есть `sessionId` необязателен, и по документации CallTouch при его отсутствии
источник берётся из utm-меток — они в payload уже были. Ломала именно пустая строка.

Масштаб по логам: **98 отказов** с нарушением `sessionId` на 10 сайтах —
evolute 42, service.tank 11, service.genesis 9, service-toyota 7, exeed 7, bodyshop 6,
geely 5, bmw 5, haval 4, hyundai 2. Письмо дилеру при этом уходило всегда
(`$form->send()` идёт до CallTouch), так что терялась заявка именно в CallTouch.

### Что сделано (13 сайтов, каждый с бэкапом `form.php.bak-2026-08-04` и `php -l`)

1. `sessionId` кладётся в payload **только непустым**; источник — кука, затем поле формы.
2. `$data['Телефон'] ?? ''` — без warning'а при отсутствии поля.
3. Ранний выход при полностью пустом `$_POST` (`http_response_code(400); exit;`) — это
   боты, дёргающие `/form.php`: раньше на каждый такой запрос уходило пустое письмо
   дилеру, бессмысленный вызов CallTouch и 3-4 warning'а.

У `hyundai-service` условный `sessionId` уже был — ему добавлен только guard.
У `service.infiniti-borishof.ru` интеграции CallTouch нет вовсе (только почта) — не трогал.

Проверка: все 13 сайтов отдают 200, пустой POST — 400, и 13 тестовых пустых POST'ов
не дали **ни одного** warning'а в php-errors.log (раньше — по 3-4 на запрос).

## Не чинится кодом — нужен кабинет CallTouch

**tank-borishof.ru: CallTouch не принимает ни одной заявки.** Ответ API воспроизведён
живьём, независимо от заявок:

```
{"data":{"message":"У пользователя 66830 нет прав на просмотр данных сайта 57477"}}
```

Access-Token принадлежит пользователю, у которого нет прав на этот сайт в кабинете.
**0 успешных отправок за всю историю логов** (самый ранний файл — уже отказ, 14.04.2026)
против 16 отказов. Правка `sessionId` этого не лечит: ошибка доступа возникает до валидации полей.

Локализация (пробы с пустым телефоном, лиды не создаются):

| токен | routeKey | ответ |
|---|---|---|
| tank-borishof | `special` | нет прав (66830 → сайт 57477) |
| tank-borishof | любой чужой | тот же отказ — дело в токене, не в routeKey |
| **service.tank-borishof** | **`special`** | **валидация phone — доступ ЕСТЬ** |

То есть `routeKey='special'` сам по себе рабочий: под аккаунтом соседнего
`service.tank-borishof.ru` он открывается. У каждого сайта флота свой уникальный токен
(общих нет), и именно токен tank-borishof лишён прав.

Технически чинится заменой Access-Token на токен `service.tank-borishof.ru`, **но
без подтверждения не делаю**: неизвестно, в какой сайт кабинета попадут лиды под чужим
аккаунтом. Молча увести заявки в чужую воронку хуже явного отказа — решение за заказчиком.

### Почему «виджет открывается, а заявки с форм не идут»

Виджет CallTouch работает из браузера напрямую в кабинет по счётчику страницы
(`wxu73bkz`) — серверный токен ему не нужен, поэтому он и жив. Формы же идут через сервер,
и там у дилера **не остаётся ни одного канала**:

| канал | состояние |
|---|---|
| CallTouch (серверный API) | мёртв — нет прав у токена (см. выше) |
| Почта | в `config.php` нет ключа `address`, в `index-production.json` `emailRecipients: []` — единственный получатель `addressCC: leads@ismart.pro`, **дилера в получателях нет** |

На странице три формы двух типов:

- две классические `.js-form` → `form.php` (поля `Имя`/`Телефон`) — доходят до сервера,
  но упираются в оба мёртвых канала выше;
- промо-попап `.js-promo-form` → `/promo-lead.php` → `https://leads.ismart.pro/lead`
  (поля `name`/`phone`/`testdrive`) — отдельная новая воронка в Google Sheets.

Промо-цепочку проверил целиком, она **исправна**: обработчик привязан и запрос реально
уходит (проверено в браузере с перехватом, лид не создавался), `promo-lead.php` отвечает
корректно, секрет `.leads-secret` совпадает с ожидаемым в `leads-api` (sha256 `ee3d5425365bebb5`),
контейнер `php-fpm85` достаёт `leads.ismart.pro`. При этом в access-логе приёмника за неделю
**ноль** POST `/lead` — то есть по этой форме просто не отправляли.

Итог: заявки, которые доходят, оседают только в нашем `leads@ismart.pro` — дилеру не уходит
ничего. Нужны два решения заказчика: корректный токен CallTouch и адрес(а) дилера в
`emailRecipients`.

Проверено пробой и не подтвердилось: у `borishof-genesis.ru` учётные данные **валидны**
(легаси-routeKey `genesis.inchcape.ru` API принимает), у `borishof-voyah.ru` — тоже.

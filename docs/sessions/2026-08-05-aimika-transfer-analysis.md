# Сессия 2026-08-05 — Разбор aimika-neiro-global и что из него взяли

Разбор соседнего проекта `~/Sites/aimika-neiro-global` (AIMIKA Global) на предмет переносимого
в iSmart Platform, внедрение выбранного в kumho — и ревизия, по итогам которой часть внедрённого
снята в тот же день.

## Что за проект

TS-монорепо: Next.js 14 + Prisma/Supabase + Upstash Redis + Cloudflare R2 + Stripe + Resend.
`packages/core` (инструменты, провайдеры ИИ, энергия/лимиты/расходы), `packages/db`, `apps/web`
(~300 файлов, 41 API-роут), `apps/bot`. Стек несовместим с нашим, поэтому переносимы решения,
а не код. Автотестов там нет вообще — наш гейт `npm run verify` сильнее, при заимствовании
практик это не терять.

## Что взяли

- CSP: `object-src 'none'` и `form-action 'self'` (`action` формы приходит из JSON-контента,
  поэтому подмена цели отправки — реальный сценарий).
- `RateLimitMiddleware::pruneExpired()` — чистка отработавших счётчиков по IP.

Всё. Остальное из первоначального списка (SSRF-safe fetch, storage-порт с `remove()`,
AI-провайдеры с реестром моделей, spend-guard, защита от prompt-injection, ретеншн-крон)
для лендинга с каталогом шин не нужно.

## Чего сознательно не делали

**Host-allowlist в CSP** — [ADR-0012](../architecture/decisions/0012-csp-no-third-party-allowlist.md).
Сетевой лог kumho: Метрика `mc.yandex.ru`, карта на `/buy` — `yastatic.net`, `api-maps.yandex.ru`
(JSONP), `log.api-maps.yandex.ru`, `core-renderer-tiles.maps.yandex.net`. Хосты Яндекса меняются
без нас, промах ломает карту и рендер для Googlebot, а выигрыш нулевой, пока в `script-src` нужен
`'unsafe-inline'`.

**Антиспам формы.** По ходу выяснилось, что rate limit обходится подделкой `X-Forwarded-For`:
nginx на стейдже заголовок не выставляет, а код (`RateLimitMiddleware::getClientIp()` и его дубль
`ApiSendAction::clientIp()`) верит клиентскому. Проверено: 14 запросов с разными `X-Forwarded-For`
прошли без 429, те же 14 без заголовка упёрлись в лимит на одиннадцатом. Тот же недостоверный IP
уходит в Google Sheets (колонка `ip`) и в блок «Дополнительно» Telegram-заявки.

Чинить не стали: в плотном отрезке прод-логов (19–27 апреля, ~1 500 записей, ~300 запросов в день)
**три отправки формы**, все `200`, спам-серий нет. Honeypot, замер времени заполнения и лимит по
сессии под такой поток не окупаются и сами способны съесть живую заявку. Вернуться к этому —
когда появится спам; починка на час.

## Что сняли обратно

`APP_CSP` + `settings['security']['csp']` + переделка биндинга в `container.php` (21 строка кода
в двух репо). Механизм переопределения CSP без единого потребителя: allowlist решили не вводить,
значит и «ручка на будущее» не нужна. ADR ужат до причины «почему не ужесточаем»,
`admin-requests-security.md` — до факта «эндпоинта нет».

## Проверено

phpstan + phpunit в обоих репо; локально — заголовки, `/`, `/buy`, `/tires/ha32`, `/news`,
`/warranty` (200), рендер `/buy` с картой и метками, консоль без CSP-нарушений; gc удалил файл
возрастом 2 часа и не тронул живой счётчик, лимит по-прежнему 10 → 429. На стейдже после выкатки —
то же самое, `/api/send` с валидным CSRF и невалидным телефоном даёт 422 (реальная заявка не
отправлялась).

## Побочные находки (не наши правки, были раньше)

- Стейдж: `/sitemap.xml` → 404 от nginx (`location ~ \.(…|xml|…)$` перехватывает как статику, до PHP
  не доходит). На проде 200.
- Яндекс.Карты на kumho пишут в консоль `Invalid API key`.
- Зеркало прод-логов на стейдже (`logs/prod`) плотное только за апрель — за лето данных нет.

## Открытое

- Прод kumho (FTP) не обновлён: правки безвредны, но специально катить их незачем — уедут
  с ближайшим содержательным релизом.
- `_ip` в заявке недостоверен: либо брать `REMOTE_ADDR`, либо убрать поле совсем (им никто не
  пользуется, а это лишние персональные данные).
- Остальные deployments правки не получали.
